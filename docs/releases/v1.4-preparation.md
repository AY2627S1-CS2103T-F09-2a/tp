# Preparing the v1.4 release

The release-preparation branch is a candidate for team review. No tag or GitHub release is created by the build.

## Build and check the candidate

Use Java 25. For the release JAR, build on macOS with the Xcode Command Line Tools (`lipo`) installed:

```sh
POCO_UI_TESTS=true ./gradlew clean check coverage shadowJar
shasum -a 256 build/libs/addressbook.jar
```

On Windows, use `gradlew.bat`; display-dependent tests need a desktop session. Normal CI still runs the required
Linux, Windows and macOS checks. The `POCO_UI_TESTS` setting enables the existing JavaFX UI tests.

When built on macOS, `shadowJar` combines the Intel and ARM JavaFX native libraries into universal Mach-O
libraries. This prevents duplicate resource names from discarding one architecture. Windows and Linux libraries
remain in the same JAR. The build fails if either Mac library set is missing or `lipo` fails. A JAR built on
Linux or Windows retains the existing Intel Mac libraries; use the macOS-built candidate for the release asset.

The app needs Java 25 and runs with:

```sh
java -jar addressbook.jar
```

To enable Java assertions when running the JAR, use `java -ea -jar addressbook.jar`.
For a packaged launch, student records are stored in `data/addressbook.json` and preferences in
`preferences.json`, both relative to the folder containing the JAR, even if launched from another working
folder. Development runs use the working folder instead. `MainApp.init` resolves both paths through
`ApplicationPaths`; preferences use JSON storage, not `java.util.prefs`. Review or test a copy in a separate
folder; preserve both files before upgrading. An unreadable student file starts an empty book, which a subsequent successful mutation can save.

## Review evidence

- Guardian search and help are registered with the real command dispatcher.
- Integration tests cover guardian editing, shared guardians, searching from another filter, displayed-index
  payment, minimum-fee filtering, exact summary totals, invalid input, unchanged query files and storage reload.
- Existing JavaFX tests cover selection restoration, deletion confirmation and help display.
- The app reports `V1.4.0` and the guides describe guardian editing/search and `fees min/AMOUNT`.
- `docs/releases/v1.4-release-notes.md` contains release copy with screenshot placeholders and captions for teammates to complete.

Record the final candidate commit, test results, JAR byte count and SHA-256 in the handoff. A successful local
run does not mark a queued GitHub job successful. If macOS CI is still waiting for a runner, report that explicitly.

## Publish manually after team review

1. Review and merge the release-preparation PR. Confirm the intended release commit contains its changes.
2. Build the final release JAR on macOS from that exact commit. Run the architecture check below on the actual JAR you will attach, record its checksum, and launch that JAR with Java 25. Repeat these checks whenever the JAR changes; a previous local candidate or a Linux/Windows CI build is not sufficient.
3. Have teammates replace every screenshot placeholder with its final image and check its caption. In GitHub Releases, create tag `v1.4` at the reviewed release commit.
4. Before publishing, open both documentation links from the release notes and confirm they resolve to the reviewed `v1.4` tag. If the team chooses another tag name, update both links to that exact name and check them again. Use **Poco Book v1.4 — Alpha Release** as the title and paste the release-note Markdown.
5. Attach the verified `addressbook.jar` and its checksum. Publish the release when you have completed your review.
6. Download the published asset, compare its SHA-256, launch it with Java 25, and check the v1.4 guide links.
7. Close publication issue #104 and final verification issue #103 only once their remaining acceptance checks are met.

## Verify the final release asset

Run this on macOS from the repository root, against the final `build/libs/addressbook.jar`. It fails unless all seven packaged Mac libraries contain both required architectures. Do not publish if it fails.

```sh
(
    set -eu
    jar_path="$PWD/build/libs/addressbook.jar"
    native_check_dir=$(mktemp -d)
    trap 'rm -rf "$native_check_dir"' EXIT
    unzip -j "$jar_path" '*.dylib' -d "$native_check_dir"
    set -- "$native_check_dir"/*.dylib
    test "$#" -eq 7
    for library in "$@"; do
        architectures=" $(lipo -archs "$library") "
        case "$architectures" in *" x86_64 "*) ;; *) exit 1 ;; esac
        case "$architectures" in *" arm64 "*) ;; *) exit 1 ;; esac
        printf '%s:%s\n' "$(basename "$library")" "$architectures"
    done
    shasum -a 256 "$jar_path"
)
```

Record the output with the release commit. Attach this exact JAR and checksum; after publication, compare the downloaded asset against that checksum as required above.

The guide links in the release notes target `v1.4` and become available when that tag is created. The shared
Google Doc remains marked as an unpublished release candidate until publication; remove that candidate notice
when copying public release text if using the Doc rather than the ready-to-paste Markdown.
